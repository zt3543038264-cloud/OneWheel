# WiFi-SPI 连接上位机

实现日期：2026-09-22；上位机 0.6.1。参考指定 CYT4bb7 工程 WiFi 层的分层方式，使用当前仓库的逐飞 TC264 WiFi-SPI 引脚和模块协议。波形、姿态、任务、参数、日志继续使用现有 cfg v1 文本协议，不使用参考工程的参数表或 JustFloat 帧。本次没有加入图传。

## 接线

以下对应 [逐飞驱动定义](../../../libraries/zf_device/zf_device_wifi_spi.h)，模块是逐飞 WiFi-SPI，不是普通串口 WiFi 模块。

| 模块 | TC264 |
|---|---|
| SCK | P22_3 / SPI3 |
| MOSI | P22_0 |
| MISO | P22_1 |
| CS | P22_2 |
| INT / 握手 | P15_8 |
| RST | P23_1 |
| 5V / GND | 按模块供电标注接 5V / 共地 |

源码核对：IMU 使用 SPI0，IPS200 使用 SPI2，未发现上述 SPI3 引脚被当前应用占用。仍需核对自己车上的实际接线。INT 在本实现中作为就绪电平轮询，不占用新的 ERU 中断。

## 车端配置（首次使用必须完成）

1. 将 `code/Protocols/station_wifi_private.example.h` 复制成同目录的 `station_wifi_private.h`，填写热点名称、密码、电脑在该热点下的 IPv4 地址。该本机文件已加入 Git 忽略规则，不能公开提交凭据。
2. 默认电脑接收端口 `STATION_WIFI_PC_PORT` 为 `1349`，模块端口 `STATION_WIFI_LOCAL_PORT` 为 `6666`。电脑与模块连接同一网络，并在路由器中为模块保留固定 DHCP 地址，避免下次分配变化。
3. 将 [station_wifi_config.h](../../../code/Protocols/station_wifi_config.h) 中 `STATION_WIFI_ENABLED` 改成 `1`，再用 ADS 编译、烧录自己的配置。本次没有执行 ADS 构建或烧录。
4. 上电时模块初始化和入网在控制定时器启动前执行；失败时 WiFi 无数据。检查供电、热点和配置后停车重启，不在运行中进行阻塞重连。

默认开关为 `0`，因此现有串口固件行为保持不变。车端一次构建选择 UART2 或 WiFi 一条命令通路，不把两路命令拼接，也不同时接受两个上位机写参数。选择 WiFi 后，UART2 上位机通路不工作；要恢复无线串口，将开关改回 `0` 后重新构建烧录。SPI 的启动函数可能等待模块响应，不能把它移动进控制中断或运行中的重连流程。

## 上位机操作

1. 打开最新版，选择 **连接设置 → WiFi · SPI 模块**。
2. **车辆 WiFi 地址**填写模块从热点取得的 IP；**车辆端口**填 `6666`。
3. **本机接收地址**通常保留 `0.0.0.0`，**本机接收端口**填 `1349`。注意这里的端口必须与车端目标端口相同；车端目标 IP 必须是电脑实际的 WiFi IPv4 地址，不能填 `0.0.0.0`。
4. 保存并点击 **连接**。若 Windows 询问防火墙权限，允许应用在所用的专用网络通信。先看到“MCU 已确认”，再等待完整参数同步；仅“WiFi 已打开”不代表车辆已连接。
5. 波形、参数分组、在线应用、记录与回放仍按现有方式操作。连接预设和工作区会保存网络配置。连接设置不保存热点密码，密码只在车端本机配置中。

原串口入口仍在同一窗口。上位机一次连接一辆车；接收端绑定指定车辆 IP 和端口，不接受其他地址发来的数据。线路错误时优先检查两端 IP/端口、同网段、热点客户端隔离、防火墙和固件开关。上位机的连接/重连是重开电脑 UDP 端口，不代表能重启模块或自动修复模块入网失败。

## 调参确认、丢包与实时负担

- 沿用 Schema、参数范围、运行状态和 MCU 二次权限检查。收到成功应答才确认应用；set/save 不因超时自动重发。应答丢失时操作结果未知，应重新读取实车值后决定下一步。
- Schema 必须完整接收才发布。UDP 丢包导致不完整时，可以点击“重新握手”；不把残缺 Schema 当成完整参数表。
- 超过约 0.7 秒未收到新状态会锁住参数，WiFi 状态栏提示数据中断。连接恢复后需重新确认实时状态。停车会重复发送幂等 stop，但只有带序号状态查询确认 STOP 后才显示已停止；无线断开时不能保证远程停车送达。
- 运行阶段只在 CPU0 前台推进 SPI，每次调用至多一次事务：就绪、数据交换、UDP flush 和确认分步处理。模块忙时立即返回，不等待网络、不断循环清空接收数据，也不关闭控制中断执行 SPI。
- 1 ms 中断在 WiFi 构建中只保留接收闲置计时；姿态/控制快照和原有周期保持不变。SPI 名义速率仍取驱动的 30 MHz，普通遥测频率未因 WiFi 自动提高。
- 每个上行协议行单独发送；单次最多 512 字节 TX / 32 字节 RX，现有最长波形行不足 256 字节。模块 flush 期间同时收到的命令字节也会交给原解析器。异常长度使该链路停止推进并丢弃当前残行。
- WiFi-SPI 提高的是链路容量；实际前台耗时、丢包率和控制抖动仍需真实硬件测量，主机测试不能证明实车运行负担或稳定性。

## 验证范围

新增测试使用本机 UDP 与 Mock 车端，覆盖握手、完整 Schema、Balance 在线改参、不自动保存、状态中断锁定、停车确认、断开重连、固定对端过滤和不完整数据包丢弃。实际 C 状态机通过主机编译运行验证忙状态立即返回、数据/flush/确认顺序、双向数据保留和异常长度；原固件 cfg 主机契约同时覆盖 UART 与 WiFi 条件编译分支。

这些检查不包含 WiFi 模块硬件、射频网络、ADS/TASKING 编译或车辆闭环性能。具体本次测试与打包结果见 [验证记录](validation.md)。
