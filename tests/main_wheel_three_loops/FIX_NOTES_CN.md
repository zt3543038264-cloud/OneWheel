- 12:53:03.003439：发送角度工具要求的 37 字段 SUB。
- 12:53:03.081832：收到与首次完全相同的 39 字段 startup 订阅，距新 SUB 请求约 78.393 ms。
- 程序在这里中止。此前从未收到目标 37 字段 SUB 确认，不能说采集已经开始后换了订阅。

两份 39 字段列表逐字段和顺序完全相同。它们与请求的 37 字段不同；不是一个相同新订阅的周期公告触发报错。v1.0 已经允许收到与目标完全相同的 SUB。

v1.0 的问题是：发送新 SUB 后立刻把所有不同于目标的 SUB 都当成“订阅改变”，即使目标尚未确认、收到的仍是已知旧配置。

OneWheel `new` / `dcce786` 中，GET?、周期公告及模式配置都会发送相同格式的 MCAR SUB；没有请求号。周期公告间隔设置为 1000 ms。日志不足以区分末条旧列表具体来自 GET? 回复、周期公告还是队列延迟，也不能证明板端后来成功处理了新 SUB。修复不依赖猜测其来源。

这次日志只包含 GET?、SUB 两个发送命令，没有参数写入、Start 或 Stop。程序退出不会停止板端控制。日志没有方向测量，不能验证 Sign 或平衡效果。

## 修改范围

只修改电脑端共享通信模块的订阅握手状态；板端固件、控制参数和参数白名单不变。

1. GET? 查询到原订阅后，发送一次目标 SUB。
2. 等待目标完全匹配的确认期间，仅忽略与原订阅完全相同的列表及顺序，单独记录 OLD_SUB_BEFORE_ACK。
3. 所有过渡二进制数据仍为 UNMAPPED，不按旧列表或相同长度猜字段。
4. 除已知原列表外，任何第三种列表、重排后的原列表都继续立即中止。
5. 首次收到目标完全匹配的 SUB 后关闭旧列表例外，包括后续 RATE/STREAM 确认阶段和正式采集阶段。
6. 原列表重复出现不会延长超时，不会自动重发。超时仍失败，不能当成采集成功。

## 先停车检查通信

1. 在车上实际按 Stop，保持电机动力断开，车体可靠支撑；不要为检查通信再按 Start。
2. 完整解压此包到新的文件夹，进入其中的 main_wheel_three_loops，确认 VERSION.txt 第一行为 1.1。
3. 关闭其他上位机接收器和会改变订阅的发送程序。
4. 先离线自测：

```text
python -m unittest discover -s tests -v
```

5. 确认板端 IP 后，只检查通信。BOARD_IP 换成当前板子地址：

```text

```

此命令只配置遥测并记录，不改变 Sign、PID、模式，不发 Start/Stop 或 Save。输出文件在执行命令时的当前文件夹；如已存在，请换一个文件名。

检查结束仍保持 Stop 和电机动力断开，把终端输出和新 JSONL 交回核对。通信测试通过不等于方向或稳定性通过。如果继续超时或遇到另一种订阅，保留日志，不要删掉订阅保护来绕过。
